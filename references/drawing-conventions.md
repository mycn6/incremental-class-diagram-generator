## 内容边界

类图只回答：本次改了哪些类型、结构发生了什么变化、影响了哪些直接关系，以及哪些结构事实应传递给后续整体方案设计。不要把提交文件列表、调用时序、业务流程或部署拓扑塞进类节点。

先确定 Git 范围，再区分静态代码、测试和运行证据。关系证据不足时标记待确认，不连猜测边；扫描器无法确认不等于系统实现困难。

## 两个独立视觉维度

1. **UML 分类器结构**表达对象是什么：矩形外框、真实成员分区、可见 stereotype、字体和关系箭头分别表示类、接口、抽象类、枚举、结构体及类间关系。
2. **主体填色和边框**只表达 Git 变更状态：新增、修改、删除或未变。

不要为不同 UML 类型随意更换流程图形状，也不要用状态颜色暗示代码质量。逻辑错误、校验与测试缺口、设计问题、模式分析、优化建议和待验证事项进入独立审查报告，不在类图中生成发现框或徽标。整体方案的重点和难点由下游 `aibid-approach-diagrams` 判断。

## 字体与中文

全图使用同一个 CJK 安全字体族，由 `style_drawio.py` 的 `TEXT_FONT` 单点定义，当前为 `Microsoft YaHei`。类标题、成员分区、图例分类器样例、标题和范围说明都用它，不因为内容是英文签名就换成等宽字体。

`Consolas`、`Helvetica`、`Arial` 一类纯拉丁字体不含中文字形。中文落在这种字体上会显示为方框或替换成意外的回退字体，字号与行高也会与同页其它文字对不上。**类标题带 `[新增]`／`[修改]`／`[删除]` 前缀、空属性分区写 `（本类未声明显式属性）`、空操作分区写 `（本类未声明显式操作）`、空枚举常量分区写 `（本枚举未声明显式常量）`，图例写 `类`／`接口`／`抽象类`／`枚举`／`结构体`，这些位置都是中文**，所以整张图没有任何一处适合放纯拉丁字体。

承载中文的单元格必须显式声明 `fontFamily`，并至少包含一个 CJK 字体族。写在 `scripts/style_drawio.py` 的 `CJK_FONTS` 白名单里的字体都算数。

交付文件必须是严格 UTF-8。生成和改写 `.drawio` 只能通过文件工具或本 Skill 的脚本；走 shell 重定向、内联脚本或其它非 UTF-8 通道时，中文会被替换成 `?` 且无法从文件本身恢复。校验脚本会检查这种痕迹。

## 类型语义与变更状态

所有类型使用矩形分类器外框，关系连接外框；标题、属性、操作和枚举常量使用独立可编辑子图元，分区线使用独立原生线图元。禁止在单个 label 中使用 `────────` 等字符模拟分区。

| `kind` | 可见标记 |
| --- | --- |
| `class` | 无额外 stereotype；标题加粗；属性区和操作区 |
| `interface` | `«interface»`；以操作契约为主 |
| `abstract` | `«abstract»`；标题使用斜体；属性区和操作区 |
| `enum` | `«enumeration»`；枚举常量区和操作区 |
| `struct` | `«struct»`；字段区和操作区 |

| `change` | 可见标记 | 填充色 | 边框 |
| --- | --- | --- | --- |
| `added` | `[新增]` | `#DCFCE7` | `#16A34A` |
| `modified` | `[修改]` | `#FEF3C7` | `#D97706` |
| `removed` | `[删除]` | `#FEE2E2` | `#DC2626`，虚线 |
| `unchanged` | 无状态前缀；图例名称“未变” | `#F3F4F6` | `#6B7280` |

状态必须来自所选 Git 范围。重命名通常记为修改并注明旧路径；只有方法体变化时突出真正变化的方法，避免暗示整个类结构都改变。

成员按字段／属性和方法分区，只列与变更或关系解释有关的内容。使用 `+`、`-`、`#` 表示可见性，保留重要参数与返回类型；无法可靠映射时保留源码写法。接口没有明确属性时不生成空属性区；枚举常量必须进入 `role=class-literals`，不能混入普通属性。

未变类型只在缺少它会使直接关键关系无法理解时加入，设置 `change=unchanged` 并直接显示类型名，不加 `[未变]`。执行 Skill 的 Agent 根据源码证据自动筛选且最多扩展一跳；生成器默认不补充。标准库、框架、工具、异常、普通 DTO、方法内部临时类型和间接依赖默认排除。

## 类间关系

边从使用者或子类型指向被使用者或父类型。每条边使用 `role="relationship"` 和明确的 `relation`：

| `relation` 机器值 | 图上可见名称 | 视觉语义 |
| --- | --- | --- |
| `inheritance` | 继承 | 实线、空心三角指向父类 |
| `implementation` | 实现 | 虚线、空心三角指向接口 |
| `association` | 关联 | 实线普通箭头，可标多重性 |
| `aggregation` | 聚合 | 空心菱形位于整体端 |
| `composition` | 组合 | 实心菱形位于整体端 |
| `dependency` | 依赖 | 虚线普通箭头 |

`relation` 属性继续使用稳定的英文枚举值，供样式器、校验器和下游脚本读取；关系边的可见 `label` 必须使用上表中文名称，并与图例保持一致。

关系必须有非空 `evidence`，例如 `src/order.py: OrderService.__init__ stores OrderRepository`。不要因同文件或名称相似连线；临时局部变量通常只表示依赖，生命周期由整体控制且对象不能独立存在时才使用组合。

`evidence` 与边的两端必须讲同一件事。`evidence` 是从声明直接生成的事实串（`<文件>: <类> declares <原始目标名>`），而箭头指向的必须是同一个类——两者矛盾时边是错的，且复核者只会读 `evidence`，看不出箭头搭错了。

解析关系目标时分两级：先按声明的完整类型名匹配，再退回短名。短名被本页多个类共用时**一律不连线**，并逐条 WARN 到 stderr：

```
WARN: relation not drawn: admin.py: Admin declares User (User is claimed by 2 classes on this page)
```

选"不画"而不是"猜一个"，是因为两者的失败方式不对称：猜错画出一条与自身 `evidence` 矛盾的边，复核者读 `evidence` 时不会发现箭头搭错了；不画只是缺一条边，复核者对着源码补即可。WARN 就是让他知道该去补哪一条。

**目标不在此页不是缺陷，是既定默认**：框架基类、标准库类型、间接依赖本就排除，这类关系静默跳过、不报告。对它们逐条 WARN 只会刷出几十条噪音，把真正需要看的歧义报告淹掉。

## 布局与图例

新增和修改类型位于视觉中心，必要的未变类型位于外围，删除类型放右侧或底部。每页保持一个主要依赖方向；自动布局默认让使用者位于左侧、被使用者位于右侧，并将循环依赖放在同层。使用直角连线，跨层和回环关系走类图区外围通道。内容过多时拆页，不用缩小字体硬塞。

节点尺寸由 `scripts/text_layout.py` 按实测文字推导，不写死常量，不允许文字穿过分区线或溢出外框。机制如下：

1. **宽度**：全页共用一个宽度，取所有标题行与成员签名实测宽度的 p90，夹在 `[300, 560]`。取分位数而非最大值，是避免一条病态签名把所有列拉宽——它自己换行即可。全页单一宽度是因为 `layout_drawio.py` 按页内最大宽度排列列距，逐类宽度会让列距与节点宽度脱钩。
2. **分区高度**：`max(该分区的最小高度, 渲染行数 × 1.25 × fontSize + 2 × spacing + 余量)`。行高模型与字宽模型都是**单向高估**：只会把框算大，永不误判"装得下"。
3. **硬折行**：生成期就把放不下的签名折成多行写入 label，使逻辑行数等于渲染行数。绝不能依赖渲染器的 `whiteSpace=wrap` 去折，有两个原因：一是高度按逻辑行数算，让渲染器折行等于高度预算按 1 行算而实际渲染 6 行；二是**渲染器不会折一个没有断行机会的 token**——实测中 `+ xxxx…(a, b): None` 这种长标识符不会被折断，而是整条越过右边框。所以折行必须自己写进 label，渲染器折行能力一律不假设。
4. **超长分区**：每个分区最多 14 个渲染行，超出部分丢弃并保留一行 `… 另有 N 项`。省略号行本身也占一个渲染行，被它挤掉的成员计入 N——显示的数目必须等于真实丢弃的数目。空属性、空操作和空枚举常量分区分别写 `（本类未声明显式属性）`、`（本类未声明显式操作）`、`（本枚举未声明显式常量）`，只陈述源码声明事实；真正的解析失败、文件跳过或语法不支持进入事实清单 `warnings` 和审查报告，不写进类节点。空分区不显示省略号行。

成员过多时优先增高节点与省略提示，不要为塞下内容缩小字号。单条签名自身就超过整个行预算时保留它并让分区长高：签名再长也只有几行，而一个只显示省略号的空分区更糟。

节点尺寸在每次导出时按当时的成员重新推导，所以不存在"尺寸陈旧"这回事。在清单里补完成员后重新导出即可；不要手工改导出 XML 里的 `height`——它是派生物，改了也会在下次导出时被重算覆盖。

每页使用一个原生可编辑 `role="legend"` 容器，容器内必须放置三组真实图元，不能用一段纯文字替代：

1. UML 类型：分别用具有真实标题和成员分区的缩略分类器展示类、接口、抽象类、枚举和结构体，保留 stereotype 与抽象斜体；
2. 类间关系：分别用实际箭头展示继承、实现、关联、聚合、组合和依赖；
3. Git 状态：分别用与正式类节点一致的填色和边框展示新增、修改、删除和未变；未变色块只出现在图例，类标题不加状态前缀。

标题下写明 Git 范围、日期、是否包含未提交改动，以及自动扫描局限。实际渲染时分别检查全图方向和正常阅读尺度下的分区、文字、箭头与图例。

## 几何优化与复核

先运行样式器生成最终分类器和分区样式，再运行 `layout_drawio.py`。布局器只使用外层类节点和关系元数据：按强连通分量与依赖层级排列类节点，以层内重心排序减少交叉，为关系分配固定端口，并把复杂路径写成可编辑 `mxPoint`。嵌套分区随外框移动。最终关系路径确定后，布局器以类框和实际路径的上下边界为准收紧纵向排版：标题／范围说明、类图内容、图例依次排列，相邻区域只保留固定的 `SUPPORT_GAP`；类节点移动时关系拐点同步移动，页面高度按收紧后的内容重新计算。多页面导出不得继承原始大页面的空白坐标。最终页面宽度确定后，标题、范围说明和图例容器自动拉伸到页面有效内容宽度，图例标题同步拉伸，保证上下区域与主图等宽。

布局器检查轴对齐路径是否穿过非端点节点、贴着无关类边框、进入无关类周围 48 像素留白区，以及不同关系是否相交或共线重合。有关系的弱连通分量分别占用独立水平带，无关系类型统一放到类区下方；类区左右两侧按关系规模预留对称外围空间，外围关系分别分配源端与目标端 gutter 车道。端点车道、外围横线和路由网格按关系组的边数与节点度动态扩展。每条候选路径与已占用线段、类框及视觉留白区核对，直接路径不合格时增加中间 x 车道形成三段式狗腿。

路线选择不能在找到第一条零交叉路径后停止。布局器必须比较全部候选，依次考虑硬冲突、与无关类的距离、拐弯数和路径长度。相邻层且纵向位置相邻的关系优先保留在端点之间；跨越两个及以上纵向位置的关系视为长关系，改走左右外围。多条关系汇入同一目标时，短关系使用局部通道，长关系分散到外围，避免一条长竖线沿无关类边框或类间狭窄通道贯穿页面。

初次逐边分配仍有冲突时，布局器按确定性顺序移除冲突最多的关系并重新安排，避免早先关系永久占用关键通道。单页仍无法得到零冲突结果时，导出器自动生成“类型总览页 + 关系详图页”：总览页展示全部类型且不画关系；关系先按事实清单中经复核的中文业务主题形成不可随意拆散的紧密组，没有主题的扫描初稿再按共享端点和源码位置分组。分页器从较少页数开始组合这些组，以实际几何检查作为合格条件；主题组自身无法通过时才按关系紧密度拆开，不得按关系编号对半切分。每条可绘制关系必须且只能出现在一张详图页；事实清单仍是完整事实来源，多页面只改变呈现方式。

关系详图标题使用 `关系详图｜<中文业务主题>`。单页包含多个主题时，按关系数量与稳定主题键选择最多两个名称，以顿号连接，超过两个时加“等”。类名、文件名、关系编号保留在机器元数据中用于追溯，不直接充当可见标题；扫描器未提供主题时允许生成中文结构性初稿名称，但正式交付前必须由执行 agent 回到源码补齐主题。

XML 几何通过不等于视觉通过。必须在 draw.io 或兼容渲染器中检查字体造成的溢出、分区边界、关系标签、箭头、页面尺度以及几何检查未覆盖的遮挡。无渲染工具时明确记录“尚未完成实际渲染检查”。

## XML 语义契约

使用未压缩结构 `mxfile > diagram > mxGraphModel > root`，保留 `mxCell id="0"` 和 `mxCell id="1" parent="0"`。同页 ID 唯一。

类节点示例（几何数值是示意，真实尺寸由 `text_layout.py` 按内容算出；要紧的是结构与元数据）：

```xml
<object id="class-1" label=""
        role="class" kind="class" change="modified"
        symbol="OrderService" source="src/order.py">
  <mxCell vertex="1" parent="1" style="...">
    <mxGeometry x="40" y="180" width="285" height="210" as="geometry"/>
  </mxCell>
</object>
<object id="class-1--header" label="[修改] OrderService"
        role="class-header" for="class-1">
  <mxCell vertex="1" parent="class-1" style="...">
    <mxGeometry x="0" y="0" width="285" height="52" as="geometry"/>
  </mxCell>
</object>
<object id="class-1--attributes" label="- repository: OrderRepository"
        role="class-attributes" for="class-1">...</object>
<object id="class-1--operations" label="+ create(command): Order"
        role="class-operations" for="class-1">...</object>
```

| 对象 | 必需元数据 |
| --- | --- |
| 类外框 | `role=class`、`kind`、`change`、`symbol`、`source` |
| 类标题 | `role=class-header`、`for=类ID`，mxCell parent 为类 ID |
| 属性分区 | `role=class-attributes`、`for=类ID`；接口和枚举可省略 |
| 操作分区 | `role=class-operations`、`for=类ID` |
| 枚举常量分区 | `role=class-literals`、`for=枚举类ID`，仅枚举必需 |
| 分区线 | `role=class-separator`、`for=类ID`，使用独立原生线图元 |
| 关系 | `role=relationship`、`relation`、`evidence`、有效 source/target |
| 包／模块 | `role=package`，仅在源码确有命名空间时使用 |
| 标题 | `role=decoration` |
| 图例容器 | `role=legend`，每页恰好一个 |
| 图例节点 | `role=legend-item`、`legend_group=uml-type/change`、稳定 `legend_key` |
| 图例分区 | `role=legend-item-section`，parent 为 UML 图例节点 |
| 图例关系边 | `role=legend-edge`、`legend_group=relationship`、稳定 `legend_key`，使用实际箭头样式 |
| 图例文字 | `role=legend-text`，用于组名和必要说明 |

边使用 `edge="1"`、有效 source/target 和 `relative="1"` geometry；节点使用 `vertex="1"` 和正尺寸 geometry。类分区通过 mxCell parent 归属外层类节点，关系只连接外层类 ID。普通范围说明使用 `role=note`；代码审查问题不得使用 draw.io 对象承载。

图内对象只承载图的语义。工具的运行诊断——歧义的关系、跳过的文件、扫描不到的类型——走 stderr，不得写进图内任何对象。`role=note` 的范围说明只描述这张图覆盖了哪些维度，不报告本次扫描的运行状态：读图的人没法照着"丢了 3 条关系"去做任何事，而运行状态会让图的文字随每次扫描浮动。

## 脚本职责边界

`style_drawio.py` 只根据显式 `kind`、`change`、分区角色和 `relation` 应用分类器、分区、状态颜色和关系箭头。它不推断类语义或关系，不调整作者布局，不自动布线，也不生成审查内容。它写入的只能是 `TEXT_FONT` 这个 CJK 安全字体，不得把作者写的中文文本覆盖成纯拉丁字体。重复运行必须保持结果一致，并保留自定义对象和连线路径。

`layout_drawio.py` 负责外层类节点坐标、关系端口、显式直角拐点和启发式几何检查；嵌套分区随父节点移动。它不修改类或关系语义，也不声称解决文字和渲染器产生的所有遮挡。重复运行必须保持结果一致。

`validate_drawio.py` 检查 XML、元数据、分类器分区、状态样式、关系箭头和真实图形图例是否齐全且样式匹配，并检查文件是严格 UTF-8、含中文的单元格声明了 CJK 字体、文本里没有 `?` 形式的编码丢失痕迹。它还按 `text_layout.py` 的同一字宽模型，检查每个标签是否装得进它的节点几何与分区几何——文字溢出到框外现在是一条可计算、硬失败的规则。

编码那项是启发式：纯 ASCII 之间夹一个 `?` 抓不到。尺寸检查的残余不确定性只在字宽表的精度和真实字体回退（非 Windows 环境没有雅黑，拉丁字宽会变），模型本身是单向高估的，所以不会漏报溢出。它仍然不能证明：

- Git 范围或源码证据选择正确；
- 成员、职责和关系符合业务语义；
- 审查报告中的问题、设计模式或优化建议判断合理；
- 实际渲染的行高与字宽就是这样，字体没有回退到别的字面；
- 图的拓扑在当前层次、页面和固定对象约束下必然可做到零交叉，因而图面可读；
- 后续整体方案设计正确。

这些内容必须结合源码、测试、运行证据和实际 draw.io 渲染分别复核。

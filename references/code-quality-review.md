## 适用方式与证据

本参考用于用户要求质量审查、合并前评审、质量评分、整改跟踪或重构方案时。审查的目标是可重复、可量化、可追溯的设计质量结论，不是罗列代码风格偏好。

先建立审查范围清单，再看类图，最后深入代码。每个报告项至少包含：完整中文类别、目标类、文件与行号或符号、结论、代码证据、影响、建议和验证方式。无法从代码静态确认的事实归入“待验证事项”，不能以猜测计分。

默认排除自动生成代码、配置文件、第三方依赖和无关改动；若它们影响本次设计关系，则在范围清单中说明纳入理由。类图应覆盖清单内的全部核心类型，并由人工核对成员和关系。

## 报告问题与方案图交接

类图只展示结构、关系与 Git 状态，不承载代码问题、设计观察、严重度或重难点。所有问题和建议进入独立审查报告，使用“逻辑错误、校验缺口、测试缺失、设计问题、模式分析、优化建议、待验证事项”等完整中文类别，不使用需要额外解释的缩写。

逻辑错误、校验缺口和设计问题必须有明确代码证据；证据不足时归入“待验证事项”，不能把猜测写成缺陷。模式分析是中性观察，必须说明代码信号、适配性和是否建议保留；模式机会必须说明稳定变化点、收益与代价。

AI 生成代码的审查重点是验证成本而不是编写难度。优先检查：实现是否符合需求；引用的 API、字段和约束是否真实存在；失败路径是否回滚并给出正确反馈；权限、租户和数据边界是否保持；测试是否会在行为错误时真正失败。不要输出“逻辑复杂”“需要协调多个步骤”之类不能驱动行动的描述。

报告项通过目标类名、源码位置或关系 ID 与类图对应，不在图中复制问题说明。审查报告必须包含“方案图输入摘要”，供 `aibid-approach-diagrams` 将类级事实重新组织为业务动作、代码节点和模型节点；摘要传递事实、问题、结构观察、模式、约束和待验证事项，不替下游判断整体方案的重点或难点。

## 评分与结论

| 维度 | 满分 | 审查重点 |
| --- | ---: | --- |
| 类设计质量 | 30 | 职责单一、方法规模、参数数量、复杂度、命名 |
| 类间关系质量 | 25 | 直接依赖、重复、继承深度、接口隔离、循环依赖 |
| 设计模式应用 | 20 | 已用模式的适配性、缺失模式的明确机会、避免过度设计 |
| 大模型边界 | 15 | 调用封装、输入校验、输出解析、异常处理、降级 |
| 可维护性 | 10 | 异常处理、日志、注释与可理解性 |
| **总分** | **100** | 各项之和 |

每项分数必须有简短理由。范围不涉及大模型调用时，将“大模型边界”标为“不适用”，其余 85 分按原权重归一化为 100 分，并在报告写明计算方式；不能把未涉及的能力当作缺陷。

- 90–100：优秀，可作为团队范例。
- 80–89：良好，可记录小问题后继续优化。
- 70–79：关键问题必须整改后复审。
- 低于 70：不通过，应在重构后重新审查。

任何低于 80 的结论都必须给出可验收整改项。评分不是合并权限的替代品；仓库已有门禁或负责人决策优先。

## 设计检查项

### 类内设计

| 检查项 | 预警阈值 | 判断与处理 |
| --- | --- | --- |
| 核心职责 | 超过 3 项 | 按独立业务能力或技术角色计数；拆分类型、提取协作者或边界接口。 |
| 方法规模 | 超过 50 行 | 结合分支和职责判断，提取子方法或独立策略。 |
| 参数数量 | 超过 5 个 | 不计 `self`／`this`；考虑参数对象或上下文对象。 |
| 圈复杂度 | 超过 10 | 用复杂度工具或清晰分支证据确认；拆分条件或策略。 |
| 命名 | 名词类、动宾方法不清晰 | 结合职责调整名称，不能只做字面替换。 |

阈值是设计审查触发信号，不是脱离上下文的硬性错误。若保留超阈值实现，报告中说明原因和风险控制。

### 类间关系

| 检查项 | 预警阈值 | 判断与处理 |
| --- | --- | --- |
| 直接依赖 | 超过 5 个协作类型 | 区分值对象与真实协作依赖；考虑门面、中间层、事件或接口。 |
| 重复实现 | 两处相似逻辑超过 20 行 | 比较语义和控制流，不以变量改名掩盖重复；评估提取。 |
| 继承深度 | 超过 3 层 | 明确复用或多态收益；优先评估组合。 |
| 接口隔离 | 实现类被迫实现无用方法 | 按调用方拆分接口。 |
| 循环依赖 | 任意实际依赖环 | 给出完整环路与引用位置，使用接口、事件或第三方协调者解除。 |

### 共性提取

出现以下任一信号时必须做专项检查：多个类型共享父类逻辑；拥有相同方法签名及相似实现；或重复实现同一套接口方法。给出重复位置、共性、候选方案（抽象基类／接口／工具类／策略类）、提取后类型名与反例或代价。只有稳定的共性才提取；不要为一次性相似代码制造抽象层。

### 大模型调用边界

仅当范围存在大模型或生成式 API 调用时审查：

1. 调用是否封装在独立的 Service、Client 或适配器中；
2. 输入是否在代码层完成结构、长度、权限或业务校验；
3. 输出是否有结构化解析、校验和异常处理；
4. 失败是否有与业务匹配的重试、默认值、人工介入或明确失败反馈。

“模型会自行处理”不是校验、解析或降级策略。

## 设计模式判断

先检查当前模式是否真的解决了变化点，再评估是否存在未抽象的稳定变化。不要为了覆盖 23 种模式而推荐模式。

| 信号 | 候选模式 |
| --- | --- |
| 独立的类型分支或算法分支 | 策略 |
| 按类型创建不同实现 | 工厂 |
| 步骤一致、局部实现不同 | 模板方法 |
| 状态变化通知多个订阅方 | 观察者 |
| 为调用动态添加缓存、日志、限流 | 装饰器 |
| 请求依次经过鉴权、校验、限流等 | 责任链 |
| 全局唯一且可控的资源管理 | 单例或依赖注入容器 |
| 外部 API 与内部接口不兼容 | 适配器 |

每条建议写明：模式名称、代码位置、变化信号、改造后核心类型和交互、收益、代价与不采用时的风险。已使用模式也要审查是否被错误用于不稳定或无共享变化点的场景。

## 问题分类与报告模板

- 逻辑错误：分支、状态、返回值、事务或数据处理错误。
- 校验缺口：输入、权限、租户、数据或模型输出缺少校验。
- 测试缺失：关键、失败或边界路径缺少有效测试。
- 设计问题：职责、依赖、重复、继承或接口设计不合理。
- 模式分析：现有模式适配性或有证据的模式机会。
- 优化建议：不属于缺陷的结构与维护性改进。
- 待验证事项：缺少测试、运行或业务确认的事实。
